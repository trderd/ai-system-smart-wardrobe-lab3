# Умный гардероб — лабораторная работа 3

Локальный компонент подбирает один комплект из вещей пользователя по температуре, осадкам и поводу. Работает без сервера, платного API и подключения к погодному сервису. Погода передаётся в запросе.

Основа — [архитектура ЛР2 BlueKujira](https://github.com/BlueKujira/ai-system-smart-wardrobe). По заданию пользователя работа оформлена в отдельном репозитории; описание находится здесь, отдельного отчёта нет.

## 1. Реализованный компонент

`Recommender.recommend()` получает запрос, проверяет его, вызывает модель и формирует рекомендацию. Из схемы ЛР2 реализованы проверка входа, предобработка, инференс, прикладные правила и чтение гардероба.

| Модуль | Что делает |
|---|---|
| `app/schemas.py` | Проверяет запрос, вещи и ответ через Pydantic |
| `app/preprocessing.py` | Создаёт общий Pipeline со StandardScaler |
| `app/train.py` | Обучает небольшую модель и сохраняет свой артефакт |
| `app/inference.py` | Загружает модель и оценивает нужную теплоту одежды |
| `app/wardrobe.py` | Читает только вещи указанного пользователя |
| `app/service.py` | Применяет ограничения и собирает комплект |
| `app/main.py` | Запускает компонент из командной строки |
| `app/demo.py` | Показывает нормальные запросы, ошибки и передачу человеку |

## 2. Установка и запуск

Нужен Python 3.12. Команды выполняются из корня проекта.

```bash
git clone --branch feature/lab3-component https://github.com/trderd/ai-system-smart-wardrobe-lab3.git
cd ai-system-smart-wardrobe-lab3
python -m venv .venv
```

Активация в Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

В Linux/macOS:

```bash
source .venv/bin/activate
```

Затем:

```bash
python -m pip install -r requirements.txt
python -m app.train
python -m app.demo
python -m pytest -q
```

Отдельный запрос:

```bash
python -m app.main examples/summer.json
python -m app.main examples/winter.json
python -m app.main examples/work_rain.json
```

Свои файлы можно указать через `--wardrobe data/wardrobe.json` и `--model artifacts/thermal.joblib`.

## 3. Контракт

Запрос сохраняет поля из ЛР2:

```json
{
  "user_id": "USER_1024",
  "weather": {"temperature": 14.5, "precipitation": "rain"},
  "occasion": "work",
  "exclude_item_ids": ["ITEM_1", "ITEM_12"]
}
```

| Поле | Тип и ограничения |
|---|---|
| `user_id` | Строка `USER_` и 1–8 цифр; обязательна |
| `weather.temperature` | Число от −50 до +50 °C; обязательно; строки, bool, NaN и бесконечность отклоняются |
| `weather.precipitation` | `none`, `rain`, `snow`; по умолчанию `none` |
| `occasion` | `casual`, `work`, `sport`; по умолчанию `casual` |
| `exclude_item_ids` | До 100 строк `ITEM_` и 1–8 цифр, либо `null`; можно не передавать |

Неизвестные поля запрещены. Повторы и неизвестные, но правильно записанные ID в списке исключений не влияют на результат: список превращается в множество.

Ответ `RecommendResponse` содержит `request_id` (UUID), `user_id`, `recommendation`, `confidence`, `outfit`, `model_version`, `needs_user_feedback` и пояснение `reason`. В `outfit` у каждой вещи есть `item_id`, `category`, `score`.

- `OUTFIT_READY`: полный комплект, оценка каждой выбранной вещи не ниже 0,5.
- `NEEDS_USER_FEEDBACK`: нужна проверка пользователя. При низкой оценке показывается предварительный комплект. Если не хватает обязательной вещи или температура вне области модели, возвращается пустой список и `confidence: null`.
- `score` — оценка теплового класса вещи из `predict_proba`. Это не «точность вещи» и не оценка красоты.
- `confidence` — минимум `score` в комплекте. Это показатель для порога, не вероятность удачности всего образа.

Ошибки входа вызывают `ValidationError`; отсутствие или повреждение модели — `ModelUnavailableError`; проблема чтения гардероба — `WardrobeUnavailableError`. Отказ зависимости не заменяется успешной рекомендацией.

Командная строка выводит ошибки в stderr: `VALIDATION_FAILED`, `REQUEST_FILE_INVALID`, `MODEL_NOT_READY`, `MODEL_INFERENCE_FAILED`, `WARDROBE_NOT_READY`. Код завершения: 0 — типизированный ответ, включая передачу пользователю; 2 — неверный ввод; 3 — отказ зависимости. HTTP-коды здесь не используются: веб-сервера пока нет.

## 4. Модель и данные

Модель — логистическая регрессия scikit-learn: по температуре оценивает три класса `light`, `medium`, `warm`. Перед ней стоит StandardScaler. Они обучаются и сохраняются одним Pipeline; параметры нормализации не пересчитываются на новом запросе. Параметры: `C=10`, `max_iter=1000`, `random_state=42`. Версия: `wardrobe-lr-1.0.0`.

`data/thermal_train.csv` — 56 синтетических примеров, температуры от −20 до +35 °C с шагом 1. Учебные метки заданы заранее: ниже +8 — `warm`, от +8 до +20 включительно — `medium`, выше +20 — `light`. Модель обучается на этих метках; при инференсе используются обученные коэффициенты, а не подстановка постоянного ответа. Эти границы — условность учебного набора, а не универсальные нормы комфорта.

`data/wardrobe.json` — 17 вымышленных вещей: 16 для `USER_1024` и одна чужая вещь для проверки разделения пользователей. У каждой вещи заданы категория, теплота, допустимые поводы, осадки и температурный диапазон. `examples/*.json` — отдельные сценарии работы. Реальных персональных данных нет.

Команда обучения создаёт `artifacts/thermal.joblib` и `artifacts/thermal.json`. В манифесте записаны версия, диапазон, число примеров, версия scikit-learn и SHA-256 модели и данных. Веса и `.venv` не отправляются в Git. Чтобы получить доверенный артефакт, выполните `python -m app.train` из исходников. После смены библиотек пересоздайте модель. Не загружайте неизвестные joblib: они способны выполнять код, а SHA-256 проверяет целостность, но не безопасность.

## 5. Прикладные правила

После модели сервис:

1. Берёт только вещи текущего пользователя.
2. Исключает указанные ID и вещи, не подходящие по поводу, осадкам или диапазону температуры.
3. Выбирает по одной вещи категорий `top`, `bottom`, `shoes`. При температуре ≤ +15 °C или осадках дополнительно требует `outerwear`.
4. В каждой категории выбирает вещь с наибольшей оценкой её теплового класса. При равенстве — с меньшим ID в строковой сортировке.
5. При `confidence < 0.5` выставляет `needs_user_feedback=true`. Ровно 0,5 допускает готовую рекомендацию. Если обязательной вещи нет, полного комплекта не выдаёт.

Модель оценивает теплоту; проверка дресс-кода, комплектности и исключений — обычные правила. Программа предлагает комплект, но не покупает вещи и не отправляет запросы оператору скрытно.

## 6. Проверки

Фактический журнал: [docs/test_results.txt](docs/test_results.txt). Пройдено **34 теста**. При тестировании модель обучается во временном каталоге, внешняя сеть не требуется.

| Случай | Ожидаемое и проверенное поведение |
|---|---|
| Лето +28,5 °C | Лёгкие верх, низ, обувь; `OUTFIT_READY` |
| Зима −8,5 °C, снег | Другие вещи, включая зимнюю куртку |
| Работа +14,5 °C, дождь | Только вещи с допуском `work`, включая пальто |
| Исключена единственная подходящая обувь | Пустой комплект, запрос участия пользователя |
| Дождь при летней температуре | Летние кроссовки не предлагаются; отказ из-за отсутствия обуви |
| Спорт, пустой или чужой гардероб | Чужие вещи не используются; запрос участия пользователя |
| −50 и +50 °C | Контракт принимает, модель отказывается от экстраполяции |
| Вне границ, строка, bool, NaN, inf | Ошибка входного контракта |
| Неверный ID, повод, осадки, лишнее поле | Ошибка валидации |
| Нет модели или артефакт повреждён | Явная ошибка, без ложного успеха |
| Искусственный сбой зависимости | `MODEL_INFERENCE_FAILED` |
| Оценка 0,4 / ровно 0,5 | Проверка пользователем / готовый комплект |
| Неверные оценки модели | NaN, значения вне диапазона и неверная сумма отклоняются |
| Нет или повреждён JSON гардероба | `WARDROBE_NOT_READY` |
| Повторный запрос после другого запроса | Тот же комплект и оценки, StandardScaler не переобучается |
| Неполный ответ с `OUTFIT_READY` | Отклоняется выходной схемой |
| Неверный ввод через CLI | Код 2 и JSON ошибки; успешный ответ отсутствует |

## 8. Изменения относительно ЛР2 и ограничения

Основные блоки архитектуры сохранены. Для изолированного запуска вместо БД используется локальный JSON, а погода вводится явно. Схемы находятся в `app/schemas.py` и не зависят от FastAPI. Неполный комплект явно обозначается как `NEEDS_USER_FEEDBACK`; для невычисленной оценки допускается `null`, добавлено поле `reason`. В исходном примере исправлена запись списка исключений на один корректный JSON-массив.

Распознавание фото, подбор цветов, история предпочтений, REST API, БД и мониторинг пока не реализованы. Модель использует только температуру; осадки и повод учитываются правилами. Влажность и ветер не учитываются. Учебные ограничения одежды тоже условны: не следует считать рекомендации проверкой безопасности для экстремальной погоды.

Успешные функциональные тесты не подтверждают F1 ≥ 0,65, Precision ≥ 0,68, задержку < 200 мс или доступность 99,9% из ЛР2. Для следующих работ нужны реальные обезличенные оценки комплектов, раздельные train/validation/test, проверка качества и порога, затем подключение БД и API. Сейчас реализован минимальный работающий компонент по объёму ЛР3.
